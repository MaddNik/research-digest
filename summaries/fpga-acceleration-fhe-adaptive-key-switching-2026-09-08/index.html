FPGA Acceleration of Fully Homomorphic Encryption with Adaptive Key Switching

arXiv · September 2026 · full view ↗

Overview and Contributions

This paper (arXiv:2609.09423, submitted 8 Sep 2026, cs.CR/cs.AR) is by Zhihan Xu, Jayashree Adivarahan, Rajgopal Kannan, and Viktor K. Prasanna of the University of Southern California and the DEVCOM Army Research Office. It targets the key-switching bottleneck in Fully Homomorphic Encryption (FHE), specifically the CKKS scheme, on FPGA platforms.

Key-switching is required after every ciphertext multiplication and rotation and can account for roughly 80% of total FHE runtime. Two competing algorithms exist for it: the traditional Hybrid Key Switching (HKS) method and a newer method the paper calls KLSS (also known as the double-decomposition method), which reduces the number of Number-Theoretic Transforms (NTTs) needed at the cost of a larger evaluation-key memory footprint and higher arithmetic precision requirements. The relative speed of HKS versus KLSS depends on hardware parallelism, the FHE security parameter set, and on-chip memory capacity, so neither method dominates universally, especially on FPGAs where SRAM is scarce.

The paper's contributions are:

  • A memory-efficient KLSS datapath tailored to FPGAs with limited on-chip memory that avoids intermediate ciphertext transfers to off-chip memory, improving data reuse and arithmetic intensity. This is presented as the first FPGA-optimized KLSS datapath.
  • An analytical performance model that captures both computation and memory-footprint trade-offs between HKS and KLSS, showing that neither method is universally optimal during FHE evaluation.
  • An adaptive FPGA accelerator, guided by the performance model, that dynamically switches between HKS and KLSS at runtime based on ciphertext computation depth (level) and parameter configuration.
  • An implementation on an AMD Alveo U280 FPGA, evaluated across multiple FHE parameter sets and benchmarks, showing 1.84 to 3.31 times speedup in bootstrapping latency and 1.66 to 2.52 times speedup in secure image classification relative to state-of-the-art FPGA accelerators.

The authors state this is the first FPGA-based FHE accelerator that supports the KLSS key-switching method as part of a full FHE pipeline, and the first to evaluate adaptive HKS/KLSS key-switching on full end-to-end FHE benchmarks.

Background: RNS-CKKS Scheme

The paper focuses on the CKKS scheme, which supports approximate fixed-point (real or complex) arithmetic and is widely used in privacy-preserving machine learning. A message vector $m \in \mathbb{C}^{N/2}$ is scaled by $\Delta$ and encoded into a plaintext polynomial $\mathrm{Pt}$, which is encrypted into a ciphertext $\mathrm{Ct}$, written $\llbracket m \rrbracket := (c_0, c_1)$. Both $\mathrm{Pt}$ and $\mathrm{Ct}$ are polynomials of degree $N-1$ in the ring $R = \mathbb{Z}[X]/(X^N+1)$; a freshly encrypted ciphertext lives in $R_Q^2$, i.e. a pair of polynomials with coefficients modulo $Q$.

Because $Q$ is typically hundreds to thousands of bits, the Residue Number System (RNS) decomposes $Q_L$ into a product of coprime, machine-word-sized primes: $Q_L = \prod_{i=0}^{L} q_i$. Under RNS each ciphertext polynomial is represented by $L+1$ limbs (one residue per prime modulus), so a fresh ciphertext contains $2(L+1)$ limbs. This variant is called RNS-CKKS. The paper's notation, extended to cover KLSS, is summarized below.

CKKS supports the following core operations, given a second plaintext $\mathrm{Pt}'$ encoding $m'$:

  • $\mathrm{PAdd}(\llbracket m \rrbracket, \mathrm{Pt}') \rightarrow \llbracket m+m' \rrbracket = (c_0+\mathrm{Pt}', c_1)$
  • $\mathrm{PMult}(\llbracket m \rrbracket, \mathrm{Pt}') \rightarrow \llbracket m \odot m' \rrbracket = (c_0 * \mathrm{Pt}', c_1 * \mathrm{Pt}')$
  • $\mathrm{Add}(\llbracket m \rrbracket, \llbracket m' \rrbracket) \rightarrow \llbracket m+m' \rrbracket = (c_0+c_0', c_1+c_1')$
  • $\mathrm{Mult}(\llbracket m \rrbracket, \llbracket m' \rrbracket) \rightarrow \llbracket m \odot m' \rrbracket = (c_0 * c_0',\; c_0 * c_1' + c_1 * c_0') + \mathrm{KeySwitch}(c_1 * c_1', \mathrm{evk}_{\mathrm{mult}})$
  • $\mathrm{Rotate}(\llbracket m \rrbracket, d) \rightarrow \llbracket m \ll d \rrbracket = \mathrm{KeySwitch}(\psi_d(c_1), \mathrm{evk}_{\mathrm{rot}}^{(d)}) + (\psi_d(c_0), 0)$, where $\psi_d$ is the automorphism permuting coefficients by $\psi_d(i) = i \cdot 5^d \bmod N$ for $i \in [0, N)$: the coefficient at index $i$ moves to position $\psi_d(i)$.

Three ciphertext-maintenance operations are needed: key-switching (required after every Mult and Rotate, and dominated by an inner product, $\mathrm{KeyInnerProd}$, between the input polynomial and an evaluation key $\mathrm{evk}$), rescaling, and bootstrapping.

Rescaling. The plaintext scale $\Delta$ grows to $\Delta^2$ after each multiplication. Rescaling restores the scale by mapping $\llbracket m \rrbracket \in R_{Q_\ell}$ to $\llbracket q_\ell^{-1} \odot m \rrbracket \in R_{Q_{\ell-1}}$, implemented per-limb as $(c[i]-c[\ell])\, q_\ell^{-1} \bmod q_i$. It removes the last modulus $q_\ell$, consuming one multiplicative level.

Bootstrapping. When the ciphertext level reaches 0, no further multiplication is possible and bootstrapping refreshes the level, allowing arbitrarily deep circuits without returning ciphertexts to the client for decryption/re-encryption. Bootstrapping itself is dominated by many Mult and Rotate calls (hence many key-switches) and consumes $L_{\text{boot}}$ levels, so only $L_{\text{eff}} = L - L_{\text{boot}}$ levels are recovered rather than the full $L$.

Key-Switching: HKS versus KLSS

Key-switching involves several subroutines: the NTT and its inverse (iNTT), an RNS basis conversion (BConv), and the key inner product (KeyInnerProd). NTT is the finite-field analogue of the FFT, used to accelerate polynomial multiplication by moving polynomials to the evaluation domain, where multiplication is element-wise; ciphertext and plaintext polynomials are usually kept in this domain. However, BConv (basis conversion, e.g. $Q \rightarrow P$) cannot be performed in the evaluation domain, so an iNTT is required beforehand and an NTT afterward to convert back. BConv computes, for each new limb, an inner product across all limbs in the original basis, so extending one limb costs one full inner product over the original basis. $\mathrm{ModUp}$ and $\mathrm{ModDown}$ denote basis conversions that increase or decrease the modulus, respectively.

HKS. The evaluation key $\mathrm{evk}$ is a $2 \times \beta$ matrix of polynomials, each with modulus $PQ_\ell$ (i.e. $\ell+k+1$ limbs). The input ciphertext polynomial is decomposed into $\beta$ digits of $\alpha$ limbs each; $\mathrm{ModUp}$ extends each digit from modulus $Q_{\alpha-1}$ to $PQ_\ell$. The digit vector is then multiplied against the evk matrix to perform KeyInnerProd, producing two polynomials in modulus $PQ_\ell$. Finally $\mathrm{ModDown}$ reduces the modulus back down to $Q_\ell$ ($\ell+1$ limbs). This full sequence is given as Algorithm 1 (see the Algorithms section at the end of this summary).

KLSS. Also called the double-decomposition method: the evk is decomposed into a $2 \times \beta \times \tilde{\beta}$ tensor of polynomials, each with only $\alpha'$ limbs (in a special modulus $T$). Because the BConv step in ModUp only needs to generate or extend $\alpha'$ new limbs (much smaller than the $\ell+k+1-\alpha$ limbs HKS needs), the number of required NTTs drops significantly. Prior KLSS work has shown that using a large coefficient modulus for $T$ (each $t_i$ having $\log t_i > 60$ bits) is beneficial because it keeps $\alpha'$ small, further reducing NTT count. During KeyInnerProd, KLSS multiplies and accumulates along the $\beta$ dimension similarly to HKS, producing a $2 \times \tilde{\beta}$ matrix of polynomials in $R_T$. An extra step unique to KLSS, limb recovery, then restores the number of limbs per row to $\ell+\alpha+1$ via BConv, requiring $\lceil (\ell+\alpha+1)/\tilde{\beta} \rceil$ extensions per polynomial; the polynomials in each row are aggregated along the $\tilde{\beta}$ dimension to give two polynomials of $\ell+\alpha+1$ limbs. Finally $\mathrm{ModDown}$ reduces the modulus back to $Q_\ell$ ($\ell+1$ limbs). This is given as Algorithm 2.

KLSS substantially reduces NTT/iNTT cost because $\alpha'$ can be kept small, but its BConv and KeyInnerProd cost can exceed HKS depending on the parameter regime (e.g. under small parameter sets such as Set-1, KLSS's BConv complexity can be higher than HKS's). This motivates the need for a performance model to decide which method to use, developed in a later section.

Memory-Efficient KLSS Datapath on FPGA

HKS has been studied extensively in prior FPGA work and can be implemented entirely on-chip. KLSS is newer and, prior to this paper, had not been optimized for an FPGA datapath. KLSS raises two specific challenges for FPGA implementation: (1) the decomposed evaluation key increases buffer requirements, and (2) the extra limb-recovery step requires additional basis conversions and produces a large number of intermediate ciphertext limbs that are hard to buffer on-chip. The paper proposes a memory-efficient KLSS datapath (illustrated in the paper's Fig. 1, a multi-stage decomposition/iNTT/BConv/NTT/KeyInnerProd/limb-recovery/ModDown pipeline) that avoids any intermediate ciphertext transfer to off-chip memory, targeting an FPGA device with 43 MB of on-chip SRAM.

The analysis uses the paper's practical, bootstrapping-capable, 128-bit-secure parameter set (Set-2 in Table IV, described later).

ModUp stage. The input ciphertext polynomial has $\ell+1$ limbs on-chip; after digit decomposition each digit has $\alpha$ limbs. During ModUp, BConv generates $\alpha'$ new limbs in $R_T$, giving a memory footprint of $\beta(\alpha+\alpha')$ limbs, about 13 MB. Because $R_T$ uses a large (62-bit) coefficient modulus, once the $\alpha'$ new limbs are generated the original $\alpha$ limbs can be discarded to free memory.

KeyInnerProd stage. This step must access the decomposed evaluation keys. The input ($\beta\alpha'$ limbs) and output ($2\alpha'\tilde{\beta}$ limbs) together need about 15 MB of buffer. However, KLSS requires $2\beta\tilde{\beta}$ evk polynomials of $\alpha'$ limbs each, for a total evk size of roughly 35 MB, which exceeds remaining on-chip capacity. The design addresses this by reorganizing the evk as a 2-D $\beta \times \tilde{\beta}$ matrix and partitioning it row-wise into $\tilde{\beta}$ chunks; each chunk ($2\beta\alpha'$ limbs) is streamed on-chip and multiplied against the $\beta$ input digits, producing two output digits of $\alpha'$ limbs. After $\tilde{\beta}$ iterations, all $2\tilde{\beta}$ output digits have been generated. A double-buffering strategy overlaps evk streaming with computation, requiring two evk chunks (12 MB) buffered simultaneously; combined with the roughly 15 MB input/output buffer, the total stays within on-chip SRAM.

Limb recovery / ModDown stage. A naive implementation would BConv all $2\tilde{\beta}$ digits at once, needing both the input ($2\tilde{\beta}\alpha'$ limbs) and output ($2(\ell+\alpha+1)$ limbs) buffered simultaneously, about 38 MB total, which is too much memory pressure. Instead the design fuses limb recovery with ModDown: rather than recovering all $\ell+\alpha+1$ limbs at once, it first recovers only the $\alpha$ limbs needed for each ModDown step, while the remaining $\ell+1$ limbs are generated one at a time and immediately consumed for subtraction inside ModDown. This limb-by-limb fusion avoids ever buffering all recovered limbs simultaneously; only the limb-recovery input ($2\tilde{\beta}\alpha'$ limbs) and the ModDown input ($2\alpha$ limbs) need to be buffered, about 19 MB, which fits on-chip.

Overall, combining evk chunking, double buffering, and fusion of limb recovery with ModDown lets the entire KLSS key-switch execute on-chip without off-chip ciphertext round-trips, reducing both memory traffic and latency. (The source PDF's Fig. 1 diagram, showing this multi-stage pipeline with intermediate limb counts of $\alpha$, $\alpha'$, and $\ell+k$ limbs at various stages, could not be captured as a separate image asset by the extraction pipeline used for this summary; it is described here in words instead.)

Analytical Model for HKS-KLSS Selection

Building on the complexity comparison in Table II, the paper develops a performance model that maps algorithmic complexity to actual execution cycles, incorporating hardware parallelism and device memory bandwidth, in order to decide when HKS or KLSS is preferable for a given benchmark and parameter set.

The accelerator is assumed to process $dp$ coefficients per cycle (its SIMD width / number of compute lanes), performing $dp$ modular multiplications, additions, or multiply-adds per cycle, with permutation operations processed at the same throughput and on-chip memory able to supply $dp$ coefficients per cycle once data is loaded from off-chip memory.

Because KLSS benefits from a large (62-bit) coefficient modulus in $R_T$ while other operations use smaller (32-bit) coefficients, and smaller coefficients allow higher SIMD parallelism (lower DSP usage per lane) and more available ciphertext levels (less frequent bootstrapping), HKS can achieve higher parallelism than KLSS under the same resource budget. This is captured with a scaling factor $\delta$ such that

$$dp_{\text{HKS}} = \delta \cdot dp_{\text{KLSS}}.$$

The total key-switching latency is modeled as a sum over the primitive operations:

$$T_{\text{KeySwitch}} = \sum_{i \in \mathrm{OP}} T_{op_i}, \qquad \mathrm{OP} = \{\mathrm{iNTT}, \mathrm{NTT}, \mathrm{BConv}, \mathrm{KeyInnerProd}\}.$$

For each primitive, the latency is the maximum of a compute-bound term and a memory-bound term:

$$T_{op_i} = \max(T_{op_i\text{-comp}}, T_{op_i\text{-mem}}).$$

The compute time is derived directly from the algorithmic complexity $C_{op_i}$ in Table II:

$$T_{op_i\text{-comp}} = \begin{cases} C_{op_i} \cdot \dfrac{N \log N}{dp} & \text{if } op_i \in \{\mathrm{NTT}, \mathrm{iNTT}\} \\[6pt] C_{op_i} \cdot \dfrac{N}{dp} & \text{otherwise} \end{cases}$$

and the memory time is modeled as:

$$T_{op_i\text{-mem}} = F_{\mathrm{clk}} \cdot \frac{B_{op_i\text{-read}} + B_{op_i\text{-write}}}{BW_{\max}},$$

where $BW_{\max}$ is the peak off-chip memory bandwidth, $B_{op_i\text{-read}}$ and $B_{op_i\text{-write}}$ are the total read/write data volumes for that primitive, and $F_{\mathrm{clk}}$ is the clock frequency.

Motivating example. On the target Alveo U280, the design can instantiate 512 32-bit modular multipliers and 256 62-bit modular multipliers, giving $dp_{\text{HKS}} = 512$, $dp_{\text{KLSS}} = 256$, and $\delta = 2$. Assuming 460 GB/s peak HBM bandwidth and a 300 MHz clock, and evaluating the practical bootstrapping-capable Set-2 parameters, the model (plotted as latency in cycles versus ciphertext level $\ell$ in the paper's Fig. 2) shows KLSS outperforming HKS at high ciphertext levels, because the reduced limb count during ModUp lowers the cost of NTT, KeyInnerProd, and BConv. As the ciphertext level decreases, however, the KLSS digit size $\alpha'\tilde{\beta}$ approaches the HKS digit size $\ell+k+1$, eroding KLSS's algorithmic advantage; combined with HKS's higher SIMD parallelism, HKS becomes the more efficient choice at low ciphertext levels. This crossover behavior across the level range is exactly what motivates an adaptive accelerator supporting both methods and switching dynamically as the ciphertext level changes during evaluation.

The Proposed Adaptive Accelerator

The accelerator's overall architecture (paper's Fig. 3a) integrates an HBM subsystem with an HBM controller, a gather-scatter unit, a multi-bank on-chip scratchpad, a compute array, a permute unit, and a datapath scheduler that orchestrates computation and permutation tasks and performs runtime switching between KLSS and HKS based on ciphertext metadata.

Adaptive compute array (Fig. 3b). The compute array has 256 compute units and a register file holding parameters such as the modulus chain. Each compute unit contains two regular cores (each with one 32-bit modular multiplier and adder) and one KLSS core (with one 62-bit modular multiplier and adder). Every core supports configurable modular multiplication, addition/subtraction, and multiply-add (three-operand) instructions; multiply-add is used both in inner-product-style primitives (BConv, KeyInnerProd) and in (i)NTT butterfly operations. For regular execution over $R_Q$ with 32-bit coefficients, both regular cores per unit are active, giving 512-way effective parallelism ($dp_{\text{HKS}}=512$). For KLSS execution over $R_T$ with 62-bit coefficients, only the KLSS cores are active, giving 256-way parallelism ($dp_{\text{KLSS}}=256$). The modular multiplier uses a fully pipelined Barrett reduction; each 32-bit multiplier uses 11 DSPs, so the 512 regular-core lanes need $11 \times 512 = 5632$ DSPs. Given the Alveo U280's DSP budget (9024 DSPs), the 62-bit KLSS multiplier instead uses an efficient design that needs only 12 DSPs, made possible because $\alpha'$ is small, allowing the use of special Solinas primes for $R_T$; with Solinas primes the modular reduction can be implemented with shifts and additions rather than multiplications. This optimization does not apply to $R_Q$ because it uses many distinct moduli $q_i$.

Adaptive permute unit (Fig. 4). Permutation (needed for (i)NTT and for the automorphism $\psi_d$) has irregular memory access patterns and is a known bottleneck in FHE accelerators. The unit is implemented as a streaming permutation network that is rearrangeable, non-blocking, and supports arbitrary permutation patterns, with a physical throughput of 256 coefficients per cycle. It consists of two spatial permutation networks with butterfly topology (each with $\log dp$ stages of $2\times2$ switches) and one temporal permutation network (using reorder buffers to permute data across cycles); routing tables hold switch configuration bits, and an address generation unit (AGU) computes memory addresses for temporal permutations, including (i)NTT permutations from initial addresses and automorphism permutations from precomputed powers of 5. To avoid the routing complexity and timing-closure difficulty of a native 512-lane permutation network (which would need heavy inter-SLR routing and deep pipelining), the physical width is fixed at 256; during regular (HKS) execution, two 32-bit coefficients from different limbs are packed into a single 64-bit word and permuted together, yielding an effective logical throughput of 512 coefficients per cycle, while KLSS operations use the native 256-lane, 62-bit mode. This lets the permute unit support both 256-way and 512-way parallelism, matching the compute array.

Multi-bank scratchpad. The on-chip scratchpad buffers Ct/Pt limbs, twiddle factors, and evaluation keys, and must simultaneously serve requests from the gather-scatter unit (HBM traffic) and the datapath scheduler (compute array and permute unit). It is organized as eight dual-port banks, each 256 64-bit words wide, so each bank can serve either 256 62-bit coefficients or 512 32-bit coefficients per access, matching the adaptive parallelism of both KLSS and regular execution. Banks are implemented with BRAM or URAM blocks, packed and stacked to reach the required width and depth, sized specifically to hold the limbs needed by the memory-efficient KLSS datapath described earlier.

Datapath scheduler. Implemented as a state machine, it has two roles: (1) it maintains ciphertext metadata at runtime and adaptively switches between KLSS and HKS based on the current ciphertext level and pre-determined switching points derived from the performance model, invoking precompiled control sequences of primitive operations for whichever method is chosen; (2) it overlaps computation and permutation under the two different parallelism modes. During KLSS execution (256-way compute matching the 256-lane physical permute throughput), the compute array processes one limb while the permute unit processes the adjacent limb, giving full overlap during (i)NTT. During regular (512-way) execution, since compute parallelism exceeds the permute unit's physical throughput, the scheduler uses the coefficient-packing trick (two 32-bit coefficients from different limbs packed per 64-bit word) so that permutation throughput again matches compute throughput, restoring full overlap.

Evaluation

Experimental setup. The accelerator is implemented in Verilog and SystemVerilog on an Alveo U280 FPGA, synthesized, placed, and routed with Vivado/Vitis 2023.1, with the host communicating over PCIe via the XRT runtime. Benchmark input data is preloaded into HBM and results are transferred back only after kernel completion; reported latencies exclude PCIe transfer time.

Key-switching performance (Table II regime, Fig. 5). Consistent with the complexity analysis and performance model, HKS wins on Set-1 (small parameter set / low ciphertext levels) and KLSS wins on Set-2 (large parameter set / high ciphertext levels). On Set-1, HKS is about $3\times$ faster than KLSS, mainly due to HKS's higher parallelism and its lower BConv complexity when the total limb count is small. On Set-2, where ciphertext levels are much larger, KLSS is about $1.3\times$ faster than HKS, because KLSS's 62-bit arithmetic in $R_T$ reduces the limb count involved in KeyInnerProd and NTT, the dominant operations at high levels. For bootstrapping, Adaptive performs almost identically to KLSS-only: bootstrapping first restores the ciphertext level from 1 to $L=38$ via an inexpensive ModUp, and the subsequently expensive operations consume $L_{\text{boot}}$ levels, leaving $L_{\text{eff}}=23$, which is close to (and above) the HKS/KLSS switching boundary, so most of bootstrapping's operations occur at high levels where KLSS wins. The design achieves $1.84\times$ to $3.31\times$ speedup over prior FPGA accelerators on bootstrapping latency. For the RN-20 benchmark, which traverses the full ciphertext-level range multiple times (multiple rounds of bootstrapping), the Adaptive configuration achieves $2.08\times$ and $1.27\times$ speedup over HKS-only and KLSS-only respectively, because it can pick the more efficient method at every level; this yields $1.66\times$ to $2.52\times$ speedup over prior FPGA-based work on RN-20 inference. Overall, KLSS-only consistently beats HKS-only on these large/deep benchmarks because high-level operations dominate total runtime and KLSS is more efficient there, but Adaptive still further improves on KLSS-only whenever a workload spends meaningful time at both high and low levels.

Related Work

Most prior FPGA-based FHE accelerators (cited as [9], [11], [12], [22], [35]-[39] in the paper) adopt only the HKS key-switching method. Two recent ASIC accelerators, FAST [13] and HAWK [40], were the first to integrate KLSS and introduce adaptive switching between HKS and KLSS, but their designs depend on large on-chip SRAM capacity that does not map well onto memory-constrained FPGA platforms. Jin et al. [21] built the first GPU-based accelerator for KLSS. The present paper positions itself as the first FPGA-based accelerator to implement KLSS at all, and the first to evaluate adaptive HKS/KLSS key-switching on full, end-to-end FHE benchmarks (as opposed to isolated key-switch microbenchmarks).

Conclusion

The paper presents a parallelism-adaptive FPGA accelerator for FHE that supports both HKS and KLSS key-switching methods. It shows that the relative efficiency of HKS and KLSS depends on the ciphertext level, reflecting a trade-off between hardware parallelism and algorithmic complexity. Guided by an analytical performance model, the accelerator performs runtime switching between the two methods. To support KLSS efficiently despite FPGA memory constraints, the authors design a memory-efficient KLSS datapath that avoids intermediate ciphertext transfers to off-chip memory. Implemented on an Alveo U280, the adaptive design achieves strong performance across both shallow benchmarks using small parameter sets and deep workloads using large, bootstrapping-capable parameter sets. The overall conclusion is that supporting adaptive key-switching methods together with adaptive hardware parallelism improves FPGA-based FHE acceleration performance beyond what a single static key-switching method can achieve. Algorithms

The paper presents two self-contained key-switching algorithms. Both take an input ciphertext polynomial $c_{in} \in R_{Q_\ell}$ and an evaluation key $\mathrm{evk}$, and produce an output ciphertext pair $(c_0, c_1) \in R_{Q_\ell}^2$.

Algorithm 1: KeySwitchHKS(c_in, evk) -> (c0, c1)
Input:  c_in in R_{Q_l},  evk in R_{P*Q_l}^{2 x beta}
Output: (c0, c1) in R_{Q_l}^2

1:  (d_j)_{j in [0,beta)} <- Decompose(c_in)      // Decompose into beta digits
2:  for j = 0 to beta - 1 do
3:      d'_j <- iNTT(d_j)                          // alpha limbs
4:      d_hat'_j = { d_j^alpha, ..., d_j^(l+k) } <- BConv(d'_j)
5:      d_hat_j <- { d_j, NTT(d_hat'_j) }           // in R_{P*Q_l}
6:  end for
        // ModUp : R_{Q_(alpha-1)} -> R_{P*Q_l}
7:  (c_hat0, c_hat1) <- (0, 0)                      // in R_{P*Q_l}^2
8:  for j = 0 to beta - 1 do
9:      (k_hat0, k_hat1) <- evk[j]                  // j-th column of evk, in R_{P*Q_l}^2
10:     (c_hat0, c_hat1) += (d_hat_j (x) k_hat0, d_hat_j (x) k_hat1)
11: end for
        // KeyInnerProd in R_{P*Q_l}
12: for i = 0 to 1 do
13:     c_hat'_i <- iNTT(c_hat_i[0, k-1])            // in R_P
14:     c'_i = { c_i^k, ..., c_i^(l+k) } <- BConv(c_hat'_i)
15:     c_i <- c_hat_i[k, l+k] - NTT(c'_i)           // in R_{Q_l}
16: end for
        // ModDown : R_{P*Q_l} -> R_{Q_l}
17: return (c0, c1)
Algorithm 2: KeySwitchKLSS(c_in, evk) -> (c0, c1)
Input:  c_in in R_{Q_l},  evk in R_T^{2 x beta x beta_tilde}
Output: (c0, c1) in R_{Q_l}^2

1:  (d_j)_{j in [0,beta)} <- Decompose(c_in)       // Decompose into beta digits
2:  for j = 0 to beta - 1 do
3:      d'_j <- iNTT(d_j)                           // alpha limbs
4:      d_hat'_j = { d_j^0, ..., d_j^(alpha'-1) } <- BConv(d'_j)
5:      d_hat_j <- NTT(d_hat'_j)                     // in R_T
6:  end for
        // ModUp : R_{Q_(alpha-1)} -> R_T
7:  for i = 0 to beta_tilde - 1 do                   // Double decomposition
8:      (c_hat_{0,i}, c_hat_{1,i}) <- (0, 0)          // in R_T^2
9:      for j = 0 to beta - 1 do
10:         (k_hat0, k_hat1) <- evk[i][j]             // in R_T^2
11:         (c_hat_{0,i}, c_hat_{1,i}) += (d_hat_j (x) k_hat0, d_hat_j (x) k_hat1)
12:     end for
13: end for
        // KeyInnerProd in R_T
14: for j = 0 to 1 do
15:     for i = 0 to beta_tilde - 1 do
16:         cbar'_{j,i} <- BConv(iNTT(c_hat_{j,i}))
                // cbar'_{j,i} = { cbar_{j,i}^0, ..., cbar_{j,i}^(ceil((l+alpha+1)/beta_tilde)-1) }
17:     end for
18: end for
        // Limb Recovery: 2*alpha'*beta_tilde -> 2*(l+alpha+1) limbs
19: for j = 0 to 1 do
20:     c_j = { c_j^0, ..., c_j^l } <- ModDown({ cbar'_{j,0}, ..., cbar'_{j,beta_tilde-1} })
21: end for
        // ModDown : (l+alpha+1) -> (l+1) limbs
22: return (c0, c1)

Note on notation: in the pseudocode above, (x) denotes the coefficient-wise (Hadamard) product between polynomials used in the KeyInnerProd accumulation, l stands for the current ciphertext level $\ell$, and beta_tilde stands for $\tilde{\beta}$. Beyond these two key-switching procedures, the paper does not present additional formal algorithms; the memory-efficient KLSS datapath (Section III of the paper) and the runtime HKS/KLSS switching logic in the datapath scheduler (Section V-D) are both described narratively and diagrammatically rather than as separate pseudocode listings, and are covered in prose in the corresponding sections above.
