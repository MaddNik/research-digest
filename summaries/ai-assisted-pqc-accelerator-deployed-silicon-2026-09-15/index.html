AI-Assisted Design of a Post-Quantum Cryptographic Accelerator: A Deployed-Silicon Case Study

arXiv (cs.CR / cs.AR) · September 2026 · full view ↗

Overview

This paper is a case study of an agentic large language model (LLM) driving the complete design, verification, synthesis, host-software development, silicon bring-up, and security hardening of a deployed post-quantum cryptographic (PQC) accelerator. The accelerator implements a unified ML-KEM-768 key-encapsulation mechanism (FIPS 203) and ML-DSA-65 digital signature scheme (FIPS 204) with on-chip key custody, deployed on a single mid-range Xilinx Kintex-7 XC7K160T FPGA connected over PCIe Gen2 x8. The authors are Jungmin Park, Eunha Kim, Wooseop Kim, Seongjoon Cho, and Byungho Cha (Lucid Motors and EYL Inc.), and the work was submitted to arXiv (cs.CR / cs.AR) on 3 Sep 2026.

The paper has two intertwined threads. The first is a security/verification finding: known-answer tests (KATs), the standard acceptance gate for cryptographic hardware, are structurally blind to an entire class of defects in rejection-sampled signature schemes such as ML-DSA, because the number of resampling iterations (and hence the control path exercised) depends on the message being signed, while KAT vectors are fixed and only reach the reject-loop depths their own seeds happen to trigger. The authors demonstrate this concretely: their accelerator passed its full KAT regression while carrying a real defect (BUG-IDE-037), a norm check that read fewer coefficients than it should because block-RAM read latency outran the check, only detected by a later randomized adversarial soak. They replace the KAT-only gate with a byte-exact golden-reference oracle plus randomized adversarial soak, demonstrating 301,343 data-dependent signings and 779,945 total soak checks with zero escapes.

The second thread is an empirical study of LLM reliability across a real, longitudinal hardware design campaign. Because the validation gate judges the artifact and never the author, the authors argue that trust in the artifact becomes separable from the question of who (or what) wrote it, which in turn makes it meaningful to measure how well an AI assistant performed as author. Over a six month campaign (2026-01 through 2026-06) they logged 232 structured experiments in which an agentic Claude Code assistant, gated by a single human developer, drove the project from RTL to PCIe bring-up. Overall task success was 71.6%, but success fell sharply as tasks moved from documentation and research (77-85%) toward synthesis and live-hardware bring-up (50-53%), a pattern the authors attribute to an observability gradient: where the corrective signal for a task lives in something the model can read (code, logs, waveforms), it performs at software-domain rates; where the signal exists only on the physical side (DMA-engine residue, placement congestion, reset-domain asymmetry, silicon-versus- simulator semantics), reliability drops toward a coin flip.

The three headline contributions, as stated by the authors, are: (C1) a validation construction (byte-exact golden reference plus randomized adversarial soak) that closes the KAT gap for rejection-sampled signature hardware, generalized into nine explicit "honesty constraints" governing what can be claimed; (C2) the hardware-coupling gradient itself, backed by the 232-log corpus, an eight-class bug taxonomy, and ten logged episodes of "confidently wrong, then corrected" reasoning; and (C3) a silicon existence proof: a unified ML-KEM-768 + ML-DSA-65 accelerator plus key-custody hardware security module (HSM) co-resident on one XC7K160T at 98.5% slice occupancy with 49 ps of setup margin at 500 MHz, byte-exact across all six FIPS operations, that shipped through two product releases.

Background: ML-KEM, ML-DSA, and LLM-Assisted Hardware Design

ML-KEM-768 (FIPS 203) is a Module-LWE (MLWE) key-encapsulation mechanism with rank $k=3$ over the ring $R_q = \mathbb{Z}_q[x]/(x^n+1)$, with $n=256$, $q=3329$, and primitive root $\zeta = 17$. Hashing uses SHAKE128/256 and SHA3-256/512 (FIPS 202). Wire sizes are: encapsulation key 1184 bytes, decapsulation key 2400 bytes, ciphertext 1088 bytes, and shared secret 32 bytes.

ML-DSA-65 (FIPS 204) is a Fiat-Shamir-with-aborts lattice signature scheme built on MLWE and Module-SIS hardness, with $n=256$, $q = 8\,380\,417$, $\zeta = 1753$, $(k,\ell) = (6,5)$, SHAKE256 mask expansion, and rejection-sampling bounds $\gamma_1 = 2^{19}$, $\gamma_2 = (q-1)/32$, $\beta = 196$, $\omega = 55$. Wire sizes are: public key 1952 bytes, secret key 4032 bytes, and signature 3309 bytes.

Shared-primitive opportunity. Both schemes operate over rings of the identical form $\mathbb{Z}_q[x]/(x^n+1)$ with $n=256$; the number-theoretic transform (NTT) butterfly has the same structural form under both moduli, and both schemes use the same Keccak permutation for hashing. This makes resource sharing natural, and is the reason both schemes plus a key-custody module fit together on a single mid-range Kintex-7 XC7K160T.

LLM-assisted hardware design, briefly. Prior work has shown that LLMs can generate syntactically valid Verilog, close simulation-feedback loops (e.g. AutoChip, RTLFixer, VerilogCoder), and assist with verification and security-sensitive RTL repair (e.g. AssertLLM, and LLM-driven security bug fixing). To the authors' knowledge, no prior published work closes the full path, RTL generation, synthesis, host software, live-hardware bring-up, and iterative hardening, on a complete cryptographic system while also reporting a campaign-level longitudinal dataset of LLM task outcomes. This gap motivates the present study.

Motivation: Why Known-Answer Tests Cannot Catch This Defect Class

ML-DSA signing is rejection-sampled: the signer repeatedly samples a candidate signature and resamples until the candidate satisfies its norm bounds. The number of resampling iterations executed, and therefore the control path exercised inside the hardware, depends on the message being signed. Correctness is thus a property of which execution paths get exercised, not just of the final output for a handful of fixed inputs.

Known-answer tests (KATs) sample a fixed set of input/output vectors. Because the reject-loop depth reached by a KAT vector is determined entirely by how that vector happens to be constructed, a KAT suite only ever exercises the reject-loop depths that its own fixed seeds trigger. Enlarging the KAT vector set does not fix this: the coverage limit follows from how the vectors are built (their seed distribution), not from how many of them there are.

The authors demonstrate this is not a hypothetical concern. Their own accelerator passed its full KAT regression while carrying BUG-IDE-037: a rejection-sampling norm check that iterated over all 256 coefficients of each polynomial, but whose block-RAM read latency delivered the final one or two coefficients only after the accept/reject decision had already been made. The defect was reachable only at reject-loop iteration 5, for one specific message class, and every affected signature failed downstream verification. It was one of eight cataloged defect classes (Table II in the source), each caught by a different validation layer that the others miss.

Because a careful team using KAT alone as its acceptance gate would ship the same silent defect, the gap is located in the instrument (the test methodology) rather than in engineer diligence. The paper's proposed remedy is to replace the KAT-only gate with a byte-exact golden-reference oracle paired with a randomized adversarial soak that drives the rejection loop past the reach of any fixed vector set. Because this replacement gate judges artifacts and never authors, it is author-agnostic: whether the RTL was written by a human or an AI becomes a separate, answerable question, which is what motivates the paper's second research thread on AI-assisted design reliability.

Methodology: The Agentic LLM-Assisted Design Loop

Assistant and toolchain. The design assistant is Claude Code, an agentic command-line interface that gives the LLM file-system and shell tools and the ability to spawn specialist subagents. On wide-scope integration days an Opus-4.6 "team-lead" orchestrated multiple Sonnet-4.6 subagents. Across the campaign, model attributions per log were: Opus-4.8 (93 logs, 17 with a 1M-context window), Opus-4.7 (63), Opus-4.6 (47), Opus-4.5 (24), Sonnet-4.6 (3, specialist subagents), and Fable-5 (1, deep research). The assistant wrote Verilog-2001 RTL, ran Icarus Verilog (iverilog) simulation with GTKWave waveform review on failures, ran Vivado 2024.2 batch synthesis/implementation via assistant-generated Tcl scripts, maintained Python golden references for FIPS 203/204, and drove Python and C99 host libraries over XDMA PCIe DMA. A separate agent thread ran multi-agent adversarial review of critical design premises, which caught at least one wrong optimization premise in practice.

Context architecture: the persistent Markdown stack. Prompts were typically one to three sentences plus pasted tool or hardware output. A four-layer stack of persistent Markdown files was re-injected into every session:

  • Project constitution (CLAUDE.md, roughly 480 lines; tagged P2): repository layout, Verilog conventions, the XC7K160T resource budget, canonical tool commands, the logging template, and both schemes' mathematical parameters.
  • Typed persistent memory (42 topic files as of the 2026-06-26 corpus snapshot, plus a one-line index; tagged P5): each file records a single fact in YAML front matter, written unprompted by the assistant. 21 "project" files hold live status; 21 "feedback" files hold failure-distilled engineering rules with explicit "why" and "how-to-apply" fields.
  • Specialist-agent definitions (seven role files): role prompts with restricted tool allowlists.
  • Procedural skills (five skill files): checklists invoked as named commands (e.g. /update-all, /spawn-team) that make the logging discipline mechanical.

The authors report that the feedback layer of typed memory carried the most methodological value: a lesson learned in week $n$ changed assistant behavior in week $n+k$. Because these layers persist outside any single conversation, work could resume after total context-window loss without re-teaching the assistant.

A separate persistent artifact, outside the four-layer stack, was a plan-and-milestone roadmap (M1-M8bp, 76 entries). Milestones M1-M8 spanned pre-silicon work through the v1.0 release (weeks 3-12): architecture locked (M1), NTT verified (M2), all modules done (M3), Kyber (M4) and Dilithium (M5) integrated (the campaign used the pre-standardization CRYSTALS names internally), optimization (M6) and validation (M7) complete, and the accelerator-only repository release (M8). M8a-M8bp (68 finer-grained sub-milestones) were appended afterward for unanticipated PCIe bring-up, key-custody, and productization work, grouped into five themes: PCIe hardware bring-up; on-chip entropy (HRNG audit, QRNG/hybrid modes, internal-seed key generation); cycle reduction (a 125 MHz respin and datapath rework); on-die key custody (sign-from-vault, on-chip key wrap/export, a Device-DNA-rooted key-encryption key, SHAKE-based key derivation, culminating in a TLS 1.3 CertificateVerify signed through hardware custody); and productization/hardening (the BUG-IDE-037 fix, exhaustive soaks, a native C host library, and the v1.0 release). The authors explicitly state they treat this roadmap as purely structural scaffolding and do not claim it raised the per-task success rate, since the study is a single case ($n=1$).

Experiment-logging discipline. Every significant unit of work was recorded as structured JSON in llm_logs/experiments/, following a nine-field schema, with logging enforced at experiment close rather than retrospectively. The logs, milestone index, category mapping, and table generation scripts are stated to be available from the authors (credential-redacted); the logging schema and a complete v89 hardware-validation transcript are supplementary material.

The golden-reference validation spine. No RTL reached a hardware build without byte-exact agreement with the Python golden reference in simulation. The promotion ladder was:

$$\text{Sim byte-exact} \rightarrow \text{KAT pass (RTL)} \rightarrow \text{HW byte-exact (PCIe)} \rightarrow \text{adversarial soak}$$

The adversarial soak stage exercises randomized message classes outside the KAT vector set; it is what caught BUG-IDE-037, which was invisible to every earlier rung of the ladder.

Human-in-the-loop role. The developer (the paper's first author) posed every task, gated every generated artifact before it reached the simulator, synthesis tool, or physical board (roughly 50% of edit-tracked generations needed a corrective edit), supplied build reports and waveforms as corrective feedback, decided when to roll back, and made every real hardware decision. The paper frames its claim as being about the agentic loop under these human gates, not about unaided model authorship.

A reusable six-step protocol (P1-P6). The paper distills the loop into six steps intended to transfer to other schemes, accelerator domains, or FPGA/ASIC flows (full listing in the Algorithms section below): (P1) build the executable golden reference before any RTL; (P2) write a versioned project constitution; (P3) instrument with an experiment log from day one; (P4) gate every artifact by hardware coupling, concentrating review depth where physical coupling is high; (P5) convert every root-caused failure into a typed feedback rule with "why" and "how-to-apply" fields; (P6) promote artifacts only up the validation ladder, never skipping a rung. The scheme-specific investment in applying this protocol elsewhere is the golden reference and KAT vectors; the device-specific investment is the constitution's tool-command and resource-budget sections. Everything else (memory-stack schema, agent roles, logging schema, promotion ladder) is claimed to have remained unchanged through the whole campaign. Whether the protocol transfers with a similar success profile to a different team or LLM is explicitly left untested.

The methodology is also packaged as a reusable repository-skeleton template holding the constitution, the golden reference directory, the typed-memory files, the agent-role and skill scaffolds, and the JSON experiment-log schema; only the constitution and golden reference need to be rewritten per target project.

Empirical Results: The 232-Experiment Corpus

Corpus and overall success rate. The corpus, frozen at a 2026-06-26 analysis snapshot, records one intensive six-month campaign (2026-01 to 2026-06) spanning 40 task categories and 76 named milestones. Of 232 logged experiments, 166 scored success and 66 failure, an overall success rate of 71.6% (Wilson 95% confidence interval 65-77%). Generated or modified code totals approximately 26,373 lines. An experiment is scored a success when its log records the task's acceptance criterion met at close (after any in-experiment iteration and human edits): functional correctness where a functional oracle exists (byte-exact match against the FIPS reference, a passing simulation, or on-silicon validation), or the applicable pass field otherwise. Abandoned or rolled-back outcomes score as failure.

Ranking the ten buckets purely by their coupling to live silicon (documentation, rank 1, no tool execution, through integration/bring-up, rank 10, requiring live-silicon state) gives a Spearman rank correlation of approximately $\rho \approx -0.83$ against the measured success rates. The authors are careful to flag this as a descriptive pattern rather than a controlled measurement: the ranking is subjective, the buckets are neither independent samples nor equal-sized, and the corpus is a single case ($n=1$), so no significance test is attached. Model choice is called an unlikely confound, since the two lowest-success buckets were also the most concentrated in the strongest model tier (Opus-4.8). Per-bucket Wilson 95% intervals are wide (documentation 73-92%, synthesis/optimization 37-68%); only the documentation and synthesis/optimization intervals are disjoint from each other.

Iterations and one-shot rate. Iteration counts were recorded in 179 of 232 logs. The one-shot rate (accepted on the first attempt) is 57.0% (102/179); 74.3% of tasks closed within two iterations and 93.3% within five, with a mean of 2.12 iterations, median 1, and maximum 14. The three hardest tasks by iteration count were: ML-DSA/Dilithium signature top-level integration (14 iterations), a PCIe Dilithium Sign+Verify debug task (9 iterations), and a Kyber KEM integration task with six bugs in the decapsulation module (8 iterations).

Human-in-the-loop rate and footprint. Among the 179 logs recording iteration counts, 91 (50.8%) needed no manual edit and 88 (49.2%) needed at least one human correction. Among 87 logs with fine-grained intervention tags (multiple tags allowed per log): logic/RTL race correction (24), documentation fix (19), host-software fix (18), syntax/compile fix (17), parameter tuning (15), timing/placement adjustment (12), rollback/revert (8), and integration wiring (6). The authors note the largest correction classes, RTL logic/race correction, host-software fixes, and timing/placement adjustments, are exactly where a software-trained model is structurally weakest, consistent with the bucket-level finding above. The 49.2% figure is only one of five operator roles the logs measure unevenly: corrective edits (measurable, worst-case bound 37.9-60.8% accounting for missing data), rollback/restart decisions (partly measurable, 8 logged reverts), go/no-go hardware acts (weakly measurable, dozens of irreversible flashing/timing-closure decisions not individually logged), and task specification plus artifact gating (not measurable as a fraction, but the operator wrote every prompt, gated every artifact, and committed 100% of changes).

Success rate over time. Monthly success ran 100% (22/22) in January, 92% (12/13) in February, 82% (14/17) in March, and 88% (45/51) in April, then dipped sharply to 41% (18/44) in May (the hardest phase, combining PCIe bring-up, an HRNG audit, and a cycle-optimization campaign with several sub-floor or rolled-back builds), before recovering to 65% (55/85) in June as the project shifted back to hardening and documentation. The authors interpret this trajectory as reflecting task mix rather than learning: live-hardware tasks were categorically impossible before the first PCIe bitstream (2026-05-04), so the monthly curve is largely the coupling gradient expressed in time, confounded by concurrent model-version changes and accumulating design debt, which a single case cannot separate.

Compute cost. Token usage was reliably measured for one continuously active session spanning six weeks (2026-05-17 to 2026-07-02), covering 117 of 238 logged experiments by that date (49% of all logged activity). Deduplicated by message ID across the main session and 615 subagent/workflow threads: 17,877 assistant turns (9,303 main-session, 8,574 subagent) processed approximately 4.47 billion tokens: 6.3 million fresh (uncached) input tokens, 21.6 million generated output tokens, 145.1 million prompt-cache write tokens, and 4,292.2 million prompt-cache read tokens. 99.4% of processed tokens were prompt-cache reads and writes. Scaling linearly by the measured window's share of logged activity gives a campaign-order estimate of roughly 9 billion tokens processed and roughly 44 million tokens generated across the whole six-month campaign. The assistant is estimated to read roughly two orders of magnitude more than it writes (approximately 207:1), meaning compute cost is dominated by context rather than generation.

Bug taxonomy. Eight defect classes were catalogued, each caught by a validation layer that the others miss: (1) non-blocking-assignment / registered-vs-combinational handshake races, detected by simulation (Vivado silently mis-synthesizes iverilog-clean RTL); (2) host-vs-RTL misdiagnosis, detected only by live hardware A/B testing; (3) timing-closure / placement congestion, detected via the build timing report; (4) FIPS / canonical-encoding mismatches, detected by hardware byte-diff against the reference; (5) data-dependent crypto logic defects (the norm-check off-by-N class including BUG-IDE-037), detected only by multi-hour adversarial soak, invisible to KAT vectors; (6) multi-block host truncation, detected by hardware byte-diff patterns (last blocks wrong, rest exact); (7) cross-process/driver transport defects, detected by hardware A/B testing across hosts and kernels; and (8) documentation over-claims, detected by post-edit grep audits and review.

Ten episodes of "confidently wrong, then corrected." In ten logged episodes the LLM (or the developer acting on its output) reached a confident but incorrect conclusion, acted on it, and later corrected course. Five are detailed: (1) a premature "zero-failures" claim after an approximately 84,000-check soak, later shown wrong by BUG-IDE-037 surfacing in a subsequent soak, misdiagnosed twice before being proven deterministic; (2) a "driver flake" managed for months as such that was actually a stale command register (BUG-IDE-021) surviving a soft-reset; (3) draining the wrong FIFO, chasing a stuck card-to-host DMA path with two wrong remedies before a burn-op fix; (4) a "LUT-bound" diagnosis overturned by multi-agent adversarial review, revealing the real constraint was 97.49% slice occupancy (placement density); and (5) an "occasional" verification bug (called "contamination") that was actually deterministically wrong 200 times out of 200 (BUG-IDE-036). The other five involved a supposedly broken board that was actually the working one, a staged memory-style fix that became infeasible on a fallback path, a wrongly RTL-blamed secret key that was host truncation, a key-derivation function wrongly believed unable to fit the device, and a correct BRAM fix that was reverted and then un-reverted.

Lesson themes. Manual thematic coding of the logs' lessons-learned fields (not a mechanical keyword count) surfaced eight recurring, multi-theme lesson categories (approximate log tallies): verify the specific buggy phrase or count rather than a bare token (75 logs); registered-versus- combinational / non-blocking-assignment discipline, since simulators tolerate races that silicon will not (73); treating negative timing slack as a placement-congestion problem to be solved by seed sweeps rather than optimization directives (71); host-versus-RTL boundary discipline, A/B testing the host-side variable before any RTL hunt (37); reading the current build report rather than historical prose, since area/clock numbers go stale in documentation but never in the report (35); honest scoping, stating only the validation rung a claim has actually earned (29); adversarial review to challenge premises, since the costliest errors were confident false premises (28); and running a golden-reference simulation before any hardware bitstream (22).

Measured productivity, efficiency, and accuracy. The authors summarize the campaign along three axes relevant to a team considering adopting the protocol: productivity (one developer plus the assistant, roughly five to six months, approximately 26,373 lines of code generated or modified, 232 logged experiments, one deployed accelerator plus HSM); efficiency (57.0% one-shot acceptance, mean 2.12 iterations, 21.6 million generated tokens with 99.4% cache-mediated processing in the measured window, extrapolated to roughly 44 million tokens for the full campaign); and accuracy (71.6% overall experiment success, 77-85% for documentation/research versus 50-53% for synthesis and bring-up, 6/6 FIPS operations byte-exact on silicon, and a 779,945-check adversarial soak with zero failures). The authors stress that raw acceptance rates are the wrong lens for correctness, since correctness comes from the validation spine rather than from how often the assistant's first draft was accepted, and the coupling gradient is precisely what motivates the protocol's insistence on human gating.

The Artifact: Architecture, Resources, and the BUG-IDE-037 Case Study

Bitstream lineage. Three bitstream labels recur throughout the paper: v87 (an earlier deployed build, used only as a resource baseline), v88 (the frozen-corpus deployed baseline behind every Section IV hardware statistic), and v89 (the shipped release with FIPS-final wire formats).

Unified architecture. The host communicates over AXI4-Lite (a BAR0 control/status register window) and AXI4-Stream (host-to-card and card-to-host bulk data channels) via the Xilinx XDMA IP core. Three clock domains are used: a 100 MHz core domain (pqc_top_clk), a 250 MHz XDMA AXI domain (axi_aclk), and a 500 MHz PCIe transceiver domain (userclk1).

A single shared, 5-stage pipelined NTT/INTT butterfly (5-cycle latency, one butterfly issued per cycle after the pipeline fills) iterates all 7 (ML-KEM) or 8 (ML-DSA) NTT layers. Twiddle ROMs hold both moduli's tables, with the active modulus selected per transform; the twiddle multiply is reduced by a two-cycle Montgomery step, while NTT-domain multiplication uses Barrett reduction with parameters $m = 5039$, $k = 24$ for ML-KEM ($q = 3329$) and $m = 8\,396\,807$, $k = 46$ for ML-DSA ($q = 8\,380\,417$), keeping coefficients in the normal domain. ML-KEM's incomplete NTT uses a degree-one base multiply; ML-DSA's complete NTT uses a pointwise multiply.

A single Keccak-f[1600] core serves both scheme control finite-state machines and the key-custody key-wrap/DRBG functions, through a registered two-master multiplexer. An extra command-bus cycle introduced by this mux, invisible to direct-wired unit testbenches, caused a wrong-tag failure in an intermediate custody-era build (v79c), caught only on hardware.

On-die entropy (HRNG). A hardware random-number generator (qec_aggregator) supplies all internal randomness. Four off-die Americium-241 quantum-entropy chip sites (one selected at runtime) are sampled as pulse-arrival times, XOR-combined with an on-die ring-oscillator TRNG, and conditioned by a private SHA3-256 core. The conditioned 256-bit words seed a SHAKE256-based deterministic random-bit generator (DRBG) that has no Keccak core of its own, instead time-sharing the single PQC Keccak core through a bypass multiplexer under hardware mutual exclusion. Per-channel SP 800-90B health tests (repetition-count, adaptive-proportion) report status but are advisory rather than enforced in the deployed build. With a control-register bit set, ML-KEM and ML-DSA key generation draw their 32-byte seed directly from the DRBG, so the seed never crosses the PCIe bus, unlike prior PQC accelerators, which receive seeds or keys from the host.

Hardware key custody (summary only; full protocol out of scope). The FPGA die itself is the trust boundary. Private keys are generated, wrapped under a key-encryption key $\mathrm{KEK} = \mathrm{SHAKE256}(\mathrm{KEK\_SALT} \| \mathrm{DeviceDNA})$, and used entirely on-die. Only public material crosses PCIe: the public key and a wrapped blob at provisioning time, and the re-presented blob plus a digest or ciphertext at sign/decapsulate time. Private keys never leave the die. An internal-seed (zero-knowledge) provisioning mode is also supported.

BUG-IDE-037 in detail: detection, root cause, fix, and closure. A later seed-driven randomized mixed-operation soak (an approximately 2,200-vector pool) caught a verification-failing signature for one message class; a preceding approximately 84,000-check soak had passed clean, which is what prompted the premature "zero-failures" claim discussed above. A constant SHA-256 hash across reruns proved the defect deterministic rather than transient or thermal. The root cause: in the signing module's Verilog, the rejection-sampling norm check reads coefficients from the main block-RAM with 2-cycle latency, but the scan counts covering $\lVert z \rVert$, $\lVert r_0 \rVert$, and $\lVert c \cdot t_0 \rVert$ covered exactly one polynomial's worth of coefficients, so the last one or two coefficients arrived after the accept/reject decision had already been made. The specific failing vector (reject-loop iteration 5) had its sole norm-violating coefficient last in scan order; a spec-correct signer would have rejected that candidate and only accepted at iteration 8. The fix extends each scan by the BRAM latency margin: the $z$ scan bound moved from 1279 to 1281 (+2, wrapping), the $r_0$ scan bound from 1535 to 1537 (+2, wrapping), and the $c \cdot t_0$ scan bound from 1535 to 1536 (+1, linear, plus an added garbage-tail guard). On hardware, the previously failing vector then re-tested byte-exact 20 out of 20 times, and the full KAT regression (7 of 7 vectors) passed. Every affected signature is guaranteed to fail downstream verification (a fail-detectable defect, not a forgery vulnerability, per constraint H8 in the Threats to Validity section), and KAT vectors structurally cannot trigger the defect because they never sample the message class that drives the rejection loop to the specific blind-spot iteration.

Reliability closure. An 8-hour adversarial soak (c_exhaustive_8h_soak_hw) ran for 28,801.6 seconds and completed 779,945 checks with zero failures, broken down as: ML-DSA provisioning (72,625 checks), sign-from-vault-then-verify on data-dependent messages (301,343 checks), verify tamper-reject checks (37,738), ML-KEM encapsulate-then-decapsulate-from-vault (295,673), and zeroize durability checks (72,562); ML-KEM provisioning coverage (4 checks) is explicitly flagged as thin. A separate C-library soak added 186,432 further checks, also with zero failures.

Comparison with prior unified accelerators (Table V). The paper's own accelerator (labeled A0) is compared against KaLi, Dobias et al., KiD, Wang et al., and Sapphire. A0 is roughly an order of magnitude slower per operation than the fastest comparators, for three compounding, disclosed reasons: (i) A0's reported numbers are end-to-end system latency over PCIe, while comparator numbers are accelerator-core latency only; (ii) A0's PQC core runs at 100 MHz on a Kintex-7 versus 270-375 MHz on UltraScale+ parts used by comparators; and (iii) A0 serializes the NTT through a single time-shared 5-stage butterfly to fit both schemes plus key custody into a nearly full XC7K160T, so even measured in clock-independent core cycles it costs roughly 6-12 times more than parallel comparators (for example, ML-KEM Decaps at approximately 67,550 cycles versus approximately 5,500-11,000 for comparators). The authors are explicit that a PCIe-attached accelerator cannot beat AVX2 software on raw throughput by construction, since AVX2 already runs below the PCIe round-trip floor; A0's claimed value is CPU offload and hardware key custody, features no compared core provides.

The PQC-PCIe Board Implementation

Board and PCIe subsystem. The board (EYL "PQC-HSM K160," model K160-PCIe, described as a working product designation) carries the XC7K160T-FFG676-2 behind a PCIe edge connector, a Micron MT25QL128 SPI configuration flash, and the Am-241 quantum-entropy subsystem described above. Deployed builds draw approximately 5.4-5.6 W on-chip. Host attachment uses the AMD/Xilinx XDMA endpoint at PCIe Gen2 5.0 GT/s x8 (approximately 3.0 GB/s modeled effective DMA bandwidth), exposing a 64 kB BAR0 window of 32-bit AXI4-Lite registers plus one host-to-card (H2C) and one card-to-host (C2H) AXI4-Stream channel (128-bit width at 250 MHz), width-adapted across three clock-domain crossings down to the wrapper's 8-bit interface in the 100 MHz core domain. The 500 MHz userclk1 domain, chronically the tightest, closed with setup slack between $+0.041$ and $+0.049$ ns.

Reset is asymmetric: a BAR0 soft-reset resets all PQC sub-state-machines via a self-clearing 16-cycle pulse (roughly 50-100 microseconds host-observed, including the re-arm poll), but the XDMA DMA engines and the H2C clock-domain-crossing FIFO reset only on a PCIe Function-Level Reset (FLR); every bug eventually traced to the FLR-only reset domain. The physical workflow (Vivado Lab flashing, a mandatory cold power-cycle after every flash, and rebuilding the XDMA kernel module against the running kernel) was learned failure-by-failure and encoded into the persistent memory stack.

Host-device protocol. Control uses a compact bank of BAR0 registers (control, status, soft-reset, HRNG and HSM custody banks, Device-DNA readback). Dispatch is deliberately minimal: the host writes a 3-bit opcode to the control register, streams input over H2C, and reads a fixed-length result over C2H with no framing headers or length fields, since a correctly sized C2H read is itself the completion signal (the status "done" bit is only a one-cycle pulse that no PCIe-latency poll can reliably catch, and interrupts are unused; the "busy" bit is polled only as a re-arm gate).

Wire sizes (v89 FIPS-final, H2C to C2H, in bytes): ML-KEM KeyGen 32 to 1184; Encaps 1216 to 1120; Decaps 3488 to 32. ML-DSA KeyGen 32 to 1952; Sign 4064 to 3309; Verify 5293 to 0 (Verify instead reports its result via a status-register bit, a late discovery during bring-up). In internal-seed mode, KeyGen seed bytes drop to zero and custody provisioning returns a wrapped blob (nonce, tag, and ciphertext: 4096 bytes for ML-DSA-65, 2464 bytes for ML-KEM-768). Direct Sign/Decaps formats carry the plaintext secret key over H2C (a compute/migration path); custody sign/decaps-from-vault instead re-presents the host-held, on-die-wrapped blob over BAR0 vault writes on each call and unwraps it on-die.

The protocol also encodes five operational disciplines, none present in any component datasheet, each distilled from a logged silicon failure:

  • D1. Soft-reset plus an idle poll of the Verify finite-state-machine's live state before every Verify call; otherwise the second back-to-back Verify deterministically returns invalid (200 out of 200 observed; BUG-IDE-036).
  • D2. Inter-operation settle: consecutive ML-DSA operations need at least 1 ms separation. The fast path uses a busy-poll re-arm gate plus an unconditional 0.5 ms residue drain.
  • D3. A warm-up burn operation at device open: an approximately 1 kB tail left in the XDMA C2H engine survives close-then-open and soft-reset, shifting the next process's first result by one byte; one throwaway KeyGen call flushes it.
  • D4. PCIe Function-Level Reset as transport recovery: a wedged H2C path, unreachable by any drain or soft-reset, recovers via a scripted FLR in approximately 6 seconds, with no power-cycle needed.
  • D5. Single-opener serialization: the XDMA device admits only one opener (returning EBUSY otherwise); multi-client use goes through a serializing daemon.

The bring-up record: where the 50% bucket was earned. PCIe bring-up compressed into four weeks (bitstreams v11-v58b): first Gen2 x8 builds on 2026-05-04 (v11), scripted flashing on 05-17 (v13), first end-to-end PCIe operation (ML-KEM KeyGen, v18) and first byte-exact result (v22) on 05-21 after fixing X-initialized $readmemh ROMs and a Vivado multi-write-BRAM dissolution bug, all six operations finite-state-machine-complete on 05-22 (v29), byte-exactness climbing 4/6, 5/6, 6/6 across 05-26/-27/-28 (the last fix host-side, no reflash needed), reaching 6/6 at full back-to-back rate on 05-29. Three failure families dominate this record: (a) stream-handshake races in RTL (combinational request lines into register-derived readiness, one-cycle pulses against backpressure, target-switch first-byte duplication, compute-gap over-fetch), all passing Icarus Verilog simulation but failing on silicon, each fixed by registering a request line, adding a sticky flag, or adding a one-deep skid buffer; (b) host-vs-RTL misdiagnosis, described as the costliest family and the purest form of the observability problem, since host, driver, DMA, and RTL can all produce identical boundary symptoms (three "RTL bugs" turned out to be host code: an abandoned reader thread silently consuming device bytes, a C2H drain that silently no-ops off the main thread, and the host waiting for Verify result bytes that the RTL never emits over C2H, masking two RTL repair attempts until the register-level read was found; the inverse also occurred once, where a back-to-back defect presented as a driver flake but was actually RTL-behavioral); and (c) transport-layer defects (XDMA C2H short-completions, AXI-Stream padding misreads, and an approximately 1-in-20 mixed-operation H2C wedge that was self-healed by the soak harness for weeks before being root-caused, then fixed via a 500-iteration A/B test that took the wedge rate from 24 down to 1, then to zero across a 1,500-iteration confirmation run, 12,825 out of 12,825 byte-exact).

Host software stack. Four host surfaces ship with the board: a Python library covering all six operations plus custody (with D3 warm-up by default); a dependency-free, protocol-exact C99 library used as the throughput benchmark client; a serializing daemon that feeds a reference OpenSSL-3 provider capable of signing a TLS 1.3 CertificateVerify through hardware custody; and demo/validation suites including a byte-exact "check all six" gate and the self-healing soak harness. Maintaining both a C and a Python implementation was deliberate, since divergences between the two repeatedly localized transport bugs that neither stack alone could attribute.

Productization and bitstream lineage beyond the analyzed snapshot. Release v1.0 (first cut 2026-06-21 on bitstream v87) packaged the bitstream, host libraries, daemon, suites, and manual. Release v1.1 (2026-07-08) shipped bitstream v89, converting both schemes from round-3-derived encodings to the final published FIPS 203/204 standards: final key-generation seed derivations, 4-bit SimpleBitPack $w_1$ encoding, a 48-byte challenge, a signature that grew from 3293 to 3309 bytes (the only wire-visible length change), and FIPS-204 domain-separated message hashing. With v89, device signatures are byte-identical to the FIPS-204 wire format, validated against a reference oracle, so conforming external verifiers (such as liboqs or OpenSSL) accept them with no host-side converter, and the device can verify externally produced signatures directly. Release v1.1 was re-validated on the board with the full suite set and the adversarial soak, again with zero failures. All corpus-derived statistics in the Empirical Results section are quoted at the frozen 2026-06-26 snapshot (v88); Release v1.1 postdates that snapshot and, while built under the same logged methodology, is treated as lineage rather than analyzed corpus.

Related Work

LLMs for RTL generation and hardware benchmarking. Prior benchmarks (Thakur et al., VerilogEval, RTLCoder) and domain-adapted models (ChipNeMo) evaluate LLM-generated Verilog at the snippet or module level via pass@k metrics at simulation or lint time. Chip-Chat carried an LLM-co-designed microcontroller through a SkyWater 130 nm shuttle tapeout, but none of these efforts reach hardened, in-service silicon with a longitudinal outcome record.

Agentic and feedback-driven LLM hardware flows. A second line of work closes tool-in-the-loop cycles: AutoChip iterates on testbench feedback, RTLFixer repairs syntax errors, MEIC and VerilogCoder add functional debugging and planning, AssertLLM generates verification assertions, and ChatEDA orchestrates the EDA toolchain on benchmark designs. QiMeng spans RISC-V CPU design from specification to silicon but stops at bring-up of a demonstrator taped out by a separate, pre-LLM pipeline. None of these reach validated operation on deployed silicon.

LLMs for hardware security. Prior work (Ahmad et al.) uses LLMs to fix security bugs in existing RTL rather than to synthesize new cryptographic hardware. To the authors' knowledge, no prior published work carries LLM-driven design with a cryptographic end goal through to validated operation on real silicon.

Closest prior art: LLMs for PQC hardware. Two 2026 works are the closest comparators: LLM4PQC (DATE'26), which synthesizes PQC cores via feedback-driven LLM-assisted HLS refactoring, and Liao et al. (ISQED'26), the first quantitative LLM-versus-HLS comparison, reporting up to 2.6x kernel speedup for FALCON compute kernels using a human-in-the-loop prompt-iteration model. Both stop short of validated operation on deployed silicon and neither reports on-chip key custody or a structured experiment-log dataset, whereas this work continues through byte-exact silicon and adversarial soak using an agentic CLI with file/shell tools and subagents, backed by 232 structured experiment logs.

ML-KEM/ML-DSA hardware accelerators. Standalone FPGA acceleration of Kyber spans a Pareto front from compact 2-DSP/3-BRAM Artix-7 designs to pipelined high-performance designs; high-speed Dilithium designs use parallel butterflies and multiple Keccak cores. Most directly comparable are unified Kyber+Dilithium designs: KaLi (first such design, ZCU102, 270 MHz), Dobias et al. (most resource-efficient to date at 17,138 LUTs at 375 MHz), KiD, Wang et al., Carril et al. (HLS batch acceleration on a PCIe datacenter Alveo card), Beckwith et al., and Truong et al. (both FIPS-final standards, all phases, on Zynq UltraScale+). The present work claims to be, to its authors' knowledge, (1) the only such design on a mid-range Kintex-7 rather than a larger UltraScale+ part; (2) the only one integrated with on-chip key custody and HRNG-seeded on-die key generation for both schemes, since prior unified designs receive seeds and keys over the host bus; and (3) measured end-to-end over PCIe including host-driver and custody overhead, rather than only at the accelerator boundary. PUF-Dilithium also targets on-chip key custody but stops at PUF-based seed protection of ARM software. A complementary line of work masks datapaths against side-channel leakage (Beckwith et al. report side-channel-analysis protection; Dobias et al. report a first-order-masked, TVLA-evaluated datapath); this work deliberately makes no side-channel claim.

Commercial PQC silicon (mid-2026 landscape, Table VII). Dedicated PQC silicon has begun arriving in 2025-mid-2026: ST's ST54M mobile secure element (ML-KEM, ML-DSA, sampling 2026), Samsung's S3SSE2A embedded secure element (ML-DSA-65 only, sampling 2026), SEALSQ's QS7001 IoT secure element (ML-KEM, ML-DSA, shipping 2025), Microchip's MEC175xB embedded controller (ML-KEM, ML-DSA, LMS, sampling 2025), Lattice's MachXO5-NX TDQ secure-control FPGA (ML-KEM plus LMS/XMSS bitstream authentication, shipping 2025), the open-source Caliptra/Adams Bridge root-of-trust IP (unified ML-DSA-87 + ML-KEM-1024, RTL-only as of 2025), IBM's Crypto Express 8S PCIe HSM (no dedicated PQC datapath, Kyber/Dilithium only in CCA firmware, shipping since 2022), and Entrust's nShield 5 PCIe/network HSM (ML-KEM/ML-DSA/SLH-DSA with an internal-FPGA accelerator of undisclosed per-algorithm scope, firmware 13.8, 2025). The authors position their own artifact as, to their knowledge, the only documented case of full hardware datapaths for both an ML-KEM and an ML-DSA parameter set with on-die key custody at host-attached (PCIe) HSM scale.

Threats to Validity and Limitations (Nine Honesty Constraints)

The authors state nine explicit constraints, framed not as hedges but as integral parts of the scientific claim itself:

(H1) $n=1$ case study / self-reported logs. No human-only baseline was run, so the productivity and cost figures are absolute rather than comparative. Labels, lesson coding, and per-log edit/iteration fields are self-recorded, incompletely covered (179 of 232 logs), and not independently adjudicated; a different task segmentation would shift the reported percentages but not the coupling-gradient ordering. Acceptance stringency also differs by bucket (operator judgment at low coupling, byte-exact matching at high coupling), so part of the observed gradient reflects differing adjudication strictness rather than task difficulty alone. Abandoned work is scored as failure.

(H2) Single LLM family / single operator. All sessions used Claude-family models and a single developer; within this tightly coupled human-AI dyad, individual contributions are not cleanly separable, and generalizability to other LLMs, toolchains, operators, or task mixes is unknown. The bucket populations in Table I reflect this specific project's phase structure, not a controlled task distribution.

(H3) Trustworthiness from validation, not authorship. Each RTL module is trusted because it passed byte-exact golden-reference comparison and, on the deployed v88 baseline, the 779,945-check adversarial soak; the v89 release re-passed the full ladder including the soak.

(H4) Device binding, not at-rest key secrecy. Given known Xilinx 7-series bitstream-encryption weaknesses, the bitstream-embedded KEK_SALT cannot be assumed secret against a physical adversary; a hardened key store is left as future work.

(H5) Integrated-system measurements, not a throughput record. Reported operations-per-second figures are measured at the peak fast-path level; the default correctness-first path adds approximately 1 ms of inter-operation reset and drain, and the reported ML-DSA Sign figure reflects the benchmark's fixed, low-rejection message rather than a worst-case rejection count.

(H6) No side-channel resistance claims. No masking is applied to the NTT, Keccak, or sampling datapaths; this is left as future work.

(H7) Not FIPS 140-3 validated. The module is byte-exact against the FIPS 203/204 reference implementations but has undergone neither Cryptographic Algorithm Validation Program (CAVP) testing nor FIPS 140-3 validation. Similarly, while the quantum-entropy chip source's min-entropy is characterized per SP 800-90B methodology, the deployed HRNG chain as a whole has no formal entropy-source validation; the statistical batteries validate only the conditioner output.

(H8) BUG-IDE-037 is fail-detectable, not a forgery vulnerability. The defect produces signatures that fail verification (and is fixed in v84); the rare pre-fix emissions are nonetheless treated as a potential information-leakage surface, with no claim of security-neutrality.

(H9) Single-operation-at-a-time / XDMA single-opener. ML-KEM and ML-DSA share the NTT and Keccak cores, so only one operation executes at a time on the device, and the XDMA device itself permits only a single opener at a time (discipline D5).

Conclusion and Future Work

The paper's conclusion restates its two linked claims. First, the standard acceptance test for lattice-signature hardware cannot detect an entire class of defects, because ML-DSA correctness is a property of the control path exercised, while known-answer tests sample only fixed values; BUG-IDE-037 passed a full KAT regression on deployed silicon. The authors resolve this blindness by replacing the gate rather than the author: acceptance decided by a byte-exact golden-reference oracle plus randomized adversarial soak, 301,343 data-dependent signings among 779,945 total checks with zero escapes on the deployed v88 baseline. Because that construction does not depend on who wrote the RTL, it makes the question of AI authorship answerable rather than a matter of trust.

Second, across 232 logged experiments, an agentic LLM assistant drove RTL through hardening at 71.6% overall success, following a hardware-coupling gradient (77-85% for documentation/research versus 50-53% for synthesis and bring-up). The authors argue the mechanism is observability, not intrinsic difficulty: reasoning over readable artifacts cannot recover a corrective signal that exists only on the physical side of a boundary. They explicitly caveat that the slope of this $n=1$ study is "a hypothesis with a mechanism attached, not a calibrated constant." What they present as not in question is the artifact itself: a unified ML-KEM-768 and ML-DSA-65 accelerator with on-chip key custody on one mid-range XC7K160T at 98.5% slice occupancy and 49 ps of margin at 500 MHz, byte-exact across all six FIPS operations in the shipped v89 release, re-soaked with zero failures.

Future directions listed by the authors: (i) a controlled multi-operator, multi-model replication study with baselines and independent outcome adjudication, going beyond the current $n=1$ case; (ii) genuine at-rest key-encryption-key secrecy via an eFUSE-protected UltraScale+ (XCZU7EV) port, already reported as first-silicon byte-exact across all six operations under the same methodology; (iii) side-channel hardening via threshold implementation, where LLM-assisted masked-gadget generation and RTL-level leakage repair could lower implementation cost; (iv) higher-throughput multi-butterfly NTTs on larger devices, for deployments where the core rather than the PCIe round trip bounds throughput; (v) the deferred custody-protocol specification and formal security analysis, plus FIPS 140-3 and CAVP validation for regulated deployments; and (vi) context condensation, distilled digests of the slowly changing project corpus to reduce the token/context cost center identified in the empirical results, acknowledged to be in tension with the lesson that stale prose summaries have previously caused errors. The paper closes by stating that all of these directions share the same discipline: state the validation rung that actually earns a claim, and claim nothing above it.

Algorithms

The source paper does not present its procedures as numbered "Algorithm" environments with formal pseudocode; its methodology is described in prose (the reusable six-step protocol P1-P6, the validation promotion ladder, the host-device dispatch protocol, and the BUG-IDE-037 root cause and fix). To satisfy a complete algorithms reference, the four procedures below are formalized directly from that prose into self-contained pseudocode; they are faithful restatements of the described steps, not verbatim listings from the paper (which contains none).

1. The golden-reference validation promotion ladder (Section III-D).

function PROMOTE(candidate_RTL):
    # Rung 1: simulation vs. golden reference
    if not byte_exact(simulate(candidate_RTL), golden_reference_output):
        return REJECT("failed sim byte-exact")

    # Rung 2: known-answer-test regression
    if not passes_KAT(candidate_RTL):
        return REJECT("failed KAT regression")

    # Rung 3: hardware byte-exact over PCIe
    bitstream = synthesize_and_implement(candidate_RTL)
    flash(bitstream)
    if not byte_exact(query_over_PCIe(bitstream), golden_reference_output):
        return REJECT("failed HW byte-exact")

    # Rung 4: randomized adversarial soak (data-dependent messages,
    # not KAT-fixed vectors)
    soak_result = adversarial_soak(bitstream, num_checks=LARGE, randomized=True)
    if soak_result.failures > 0:
        return REJECT("failed adversarial soak: " + soak_result.details)

    return DEPLOY(bitstream)   # never skip a rung (P6)

2. The reusable six-step protocol for applying the methodology to a new scheme/device (Section III-F, P1-P6).

procedure APPLY_METHODOLOGY(target_scheme, target_device):
    # P1: executable golden reference first
    golden_reference = implement_reference(target_scheme)   # e.g. Python, byte-exact
    require: no RTL work begins before golden_reference exists

    # P2: write the constitution
    constitution = write_markdown(
        layout = repo_layout(),
        conventions = coding_conventions(),
        budget = resource_budget(target_device),
        tool_commands = canonical_tool_commands(),
        log_schema = EXPERIMENT_LOG_SCHEMA
    )

    # P3: instrument before generating
    initialize_experiment_log(schema = EXPERIMENT_LOG_SCHEMA)  # from day one

    memory = TypedMemoryStack(project_files = {}, feedback_files = {})
    for each unit_of_work in project_backlog:
        candidate = agent_generate(unit_of_work, context = [constitution, memory,
                                                             agent_roles, skills])

        # P4: gate by hardware coupling; deeper review where physical coupling is high
        approved = human_review_gate(candidate, coupling_level(unit_of_work))
        if not approved:
            edited_candidate = human_correct(candidate)
        else:
            edited_candidate = candidate

        result = PROMOTE(edited_candidate)   # ladder of procedure 1, P6: never skip a rung
        log_experiment(unit_of_work, edited_candidate, result)   # P3

        # P5: convert every root-caused failure into a typed feedback rule
        if result is REJECT:
            root_cause = diagnose(result)
            rule = TypedFeedbackRule(why = root_cause.explanation,
                                      how_to_apply = root_cause.remedy)
            memory.feedback_files.append(rule)   # persists into all future sessions

    return deployed_artifact

3. BUG-IDE-037 root-cause diagnosis and fix (Section V-D), as a procedure.

procedure DIAGNOSE_AND_FIX_NORM_CHECK_BUG(dilithium_sign_module):
    # Symptom: KAT regression passes, but a randomized adversarial soak
    # surfaces a verification-failing signature for one message class.

    failing_vector = adversarial_soak_hit         # e.g. reject-loop iteration 5
    hash_before = sha256(rerun(failing_vector))
    hash_after  = sha256(rerun(failing_vector))
    assert hash_before == hash_after               # rules out transient/thermal cause

    # Root cause: BRAM read latency (2 cycles) outruns the norm-check scan window
    for each norm in [ "||z||", "||r0||", "||c*t0||" ]:
        scan_bound = dilithium_sign_module.scan_bound[norm]
        bram_latency = 2                            # cycles
        if scan_bound < required_coeff_count(norm) + bram_latency:
            # last 1-2 coefficients arrive after accept/reject decision
            flag_as_root_cause(norm, scan_bound)

    # Fix: extend each scan bound by the BRAM latency margin
    dilithium_sign_module.scan_bound["||z||"]     += 2   # 1279 -> 1281, wrapping
    dilithium_sign_module.scan_bound["||r0||"]    += 2   # 1535 -> 1537, wrapping
    dilithium_sign_module.scan_bound["||c*t0||"]  += 1   # 1535 -> 1536, linear
    add_garbage_tail_guard(dilithium_sign_module, "||c*t0||")

    # Validation: re-run PROMOTE ladder from rung 1
    assert PROMOTE(dilithium_sign_module) == DEPLOY
    assert repeat(query_over_PCIe, failing_vector, times=20) == all_byte_exact
    assert passes_KAT(dilithium_sign_module)       # 7/7

4. Host-device dispatch protocol for a single accelerator operation (Section VI-B).

procedure DISPATCH_OPERATION(opcode, input_bytes):
    # No framing headers or length fields; tlast delimits streams.
    write_register(CTRL, opcode)              # 3-bit opcode
    stream_H2C(input_bytes)                   # host-to-card AXI4-Stream

    busy_poll(STATUS.busy)                    # re-arm gate only; STATUS.done is a
                                               # one-cycle pulse no PCIe-latency poll
                                               # can reliably catch

    if opcode == VERIFY:
        result = read_register(STATUS)[2]     # dil_valid bit, not a C2H read
    else:
        result_bytes = stream_C2H(expected_length(opcode))
        # receiving exactly expected_length bytes is itself the completion signal
        result = result_bytes

    return result
